# An EMPTY render pass costs the open driver 74x the vendor's

`vkrender MODE=empty` runs the same render pass with **no draw and nothing loaded or stored**,
isolating per-pass setup from drawing. (The probe needed a fix first: its early-return for partial
modes skipped the timing print, so this number had never been reported.)

| mode (2048) | open | vendor | ratio |
|---|---|---|---|
| **empty pass** | **0.668 ms** | **0.009 ms** | **74x** |
| render | 13.846 ms | 6.185 ms | 2.24x |
| copy | 4.006 ms | 2.858 ms | 1.40x |

## What it establishes

* **The open driver pays 0.668 ms for a render pass that draws nothing**; the vendor pays 0.009 ms.
  A large, specific, in-scope defect, 74x in relative terms.
* **It accounts for the earlier "fixed per-frame cost"** (0.85 ms open vs 0.52 vendor): that fixed
  term *is* this per-pass overhead plus submission - nothing about pixels.
* **Three distinct gaps, now separable by measurement:** per-pass setup 74x, the draw itself 2.13x
  (13.18 vs 6.18 ms), and the copy path 1.40x (4.006 vs 2.858 ms).

## Why it matters more than its size suggests

0.668 ms is 5% of one 2048x2048 render - but it is **per render pass**, not per frame. A real client
frame goes through several passes (the client's render, weston's composite), so at 60 fps that is
**8-12% of the frame budget before any pixel is drawn**. It is also the **cheapest thing to attack**,
because an empty pass has no pixel work: whatever costs 0.668 ms is pure setup, profilable without any
raster/PBE involvement.
