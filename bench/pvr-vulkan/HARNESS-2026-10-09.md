# harness.py — one run, every stage, both drivers

## Why it exists

Every previous measurement in this session looked at **one stage at a time**: a throughput probe, or a
per-job trace, or an ioctl count. That produces tunnel vision: a change to PCO cannot be seen to affect the
per-job structure, and a change to the sync path cannot be seen to affect throughput.

**This harness observes all of it in one invocation and logs one JSON record per run**, so a modification to
any one component shows up alongside everything else that moved.

## Usage

```
./harness.py <probe> <size> <count> [ENV=VAL ...] [--driver=open|vendor]
    probe   vkrender | vkheavy | cstp | cstpf | cstpi | ...
    size    surface size (vk*) or workgroup count (cst*)
    count   frames (vk*) or iterations (cst*)
    --driver=open|vendor   switch first (refuses if kwin is alive - the guard's rule)
```

## What it reports, every run

* **driver** currently bound (so records are never ambiguous)
* **speed** - ms/frame, Mpix/s, or M invocations/s, whichever the probe reports
* **correctness** - the probe's own verdict and pixel count
* **per-stage job breakdown** - every job with its duration, from the tracepoints the *bound* driver emits
  (`gpu_scheduler` for the open driver, `pvr_fence` for the vendor) - so it works under either without
  knowing which
* **critical path** - the longest job, i.e. what the frame actually waits on
* **job count** in the trace window

Every run appends a JSON record to `harness-log.jsonl` for comparison across runs and drivers.

## Two design decisions that were forced by measurement

1. **Two phases.** The job breakdown comes from a **1-frame** run and the speed from a **long** run, because
   fence pairing degrades above a few thousand jobs - measured earlier this session: it produced a
   physically impossible 168 ms median job for terrain. **One frame keeps every fence handle unique.**
2. **Phase 2 runs the caller's workload count to completion**, not against a wall-clock timer. A terminated
   run never prints its summary, and the summary is where speed and correctness come from. `cst*` probes read
   the count as *iterations*, so a small "frames" value silently measured setup overhead instead of throughput
   (101.9 vs 413.1 M inv/s on the same probe).

## The guard rule is built in

`--driver=` switches only after checking that `kwin_x11`/`kwin_wayland` are absent; otherwise it **refuses and
says so**, and still measures the bound driver. Verified:

```
switch to open: REFUSED (kwin is alive - guard would abort; refusing to unbind)
HARNESS  driver=pvrsrvkm  ...
```

**The safety requirement of the objective is therefore enforced by the tool, not by remembering to check.**
